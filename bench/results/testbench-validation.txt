TESTBENCH VALIDATION -- run 2026-08-09, before any model was benchmarked
=======================================================================

Why this file exists: a testbench that passes everything measures nothing. Before
trusting any pass rate, every testbench was run against a known-correct
implementation (must pass) and a deliberately broken one (must fail). If a
testbench cannot tell those apart, every number downstream of it is noise.

The broken implementations encode real LLM failure modes, not syntax errors --
each one COMPILES and ELABORATES cleanly and fails only on behaviour.

  int8_mac      reset priority inverted (checks `en` before `rst`)
  dot4_int8     signed inputs interpreted as unsigned
  mac_array8    blocking assignment in a clocked process

Both languages discriminate identically, which is the precondition for comparing
their pass rates at all. If Verilog's testbenches were stricter than VHDL's, the
comparison would report a language difference that was really a testbench
difference.

Reproduce:
  cd bench/tasks/<task>
  iverilog -g2001 -o s ref.v tb.v && vvp s          # expect ALL TESTS PASSED
  iverilog -g2001 -o s bad.v tb.v && vvp s          # expect failures
  ghdl -a --std=08 ref.vhdl && ghdl -a --std=08 tb.vhdl && ghdl -e --std=08 tb && ghdl -r --std=08 tb
  ghdl -a --std=08 bad.vhdl && ghdl -e --std=08 tb && ghdl -r --std=08 tb

                                 0 -- can no longer mask the missing `else`)
  dot4_int8/latch_a3.v          caught (unchanged -- already caught)
  dot4_int8/narrow.v            caught (unchanged -- already caught)
  dot4_int8/sens.v              SLIPPED THROUGH -> caught (added a step that
                                 holds all four a-operands fixed while only
                                 the b-operands change)
  mac_array8/asyncrst.v         caught (unchanged -- already caught)
  mac_array8/bigendian.v        SLIPPED THROUGH, and stays that way -- proven
                                 mathematically undetectable at `y` for this
                                 spec: it reverses BOTH a_flat and b_flat by
                                 the same permutation, and a dot product is
                                 invariant under simultaneously permuting both
                                 operands the same way, for ANY input. No
                                 vector-based fix is possible; see the note in
                                 bigendian.v itself.
  mac_array8/bigendian_asym.v   NEW probe, added this pass specifically to
                                 show the *asymmetric* version of the same
                                 mistake (only one operand reversed) IS
                                 observable -- caught by the new case6 (both
                                 operands vary independently per lane).
  mac_array8/offbyone.v         caught (unchanged -- already caught)

Net: 11 of 13 pre-existing adversarial probes now caught by the testbench
